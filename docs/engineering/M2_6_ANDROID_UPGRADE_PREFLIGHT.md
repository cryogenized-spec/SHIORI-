# M2.6 — Offline debug APK upgrade identity preflight

**Status: release blocked; physical-device acceptance not performed.**

This increment does not install an APK, handle private signing keys, read
phone data, invoke ADB, mark a release as ready or approve native SQLite
migration. It is deliberately a safe preparation stage before a real-device
upgrade rehearsal.

## Why this matters

An Android in-place upgrade normally needs the exact same application ID and
a compatible signing identity. GitHub-hosted debug builds may be signed with
different ephemeral debug certificates. Running `adb install -r` with a new
signature can fail, and uninstalling an old APK to bypass the failure can erase
SHIORI's private SQLite and WebView data. Do **not** uninstall a real-data
installation as an upgrade workaround.

Run the read-only preflight on two SHIORI *debug* APKs and their exact paired
`shiori-android-evidence.json` files obtained from CI:

```bash
python3 tools/android/compare_debug_upgrades.py \
  --previous-apk /tmp/previous/app-debug.apk \
  --previous-evidence /tmp/previous/shiori-android-evidence.json \
  --candidate-apk /tmp/candidate/app-debug.apk \
  --candidate-evidence /tmp/candidate/shiori-android-evidence.json \
  --aapt /path/to/android/sdk/build-tools/36.0.0/aapt \
  --apksigner /path/to/android/sdk/build-tools/36.0.0/apksigner
```

The script checks that each APK matches its recorded package, bytes and
bundled Rust JNI/web resources. It also runs Android SDK `aapt` and
`apksigner` independently on both APKs, checking their **actual signed
certificate, package identity, versionCode, versionName and declared permissions**
against the CI manifests. The pair must have the same public certificate
SHA-256 and the candidate versionCode must be greater. A real Android SDK
build-tools installation is required; the tool fails rather than relying
solely on potentially altered manifest metadata. It
requires distinct commit IDs, no unexpected Android permissions, and the
explicit **not release-ready** flags. It exits nonzero and prints `BLOCKED`
on a missing/tampered artifact, mismatched signing identity, same version,
downgrade or forged device-acceptance status.

The manifest is evidence generated by the same CI pipeline, **not** an
independently signed attestation. The preflight **does independently extract**
the package metadata and signing certificate from each APK with Android SDK
tools, but does not prove source reproducibility, establish trusted key
custody or test whether Android's package manager accepts an upgrade. A successful preflight alone is not permission to install on a
working phone.

## Next manual acceptance gate (disposable profile only)

Prepare a stable, securely held development signing identity outside the
repository and bump Android versionCode for the candidate. Build both APKs
under that identity; keep private signing material out of GitHub artifacts,
issues and log output. Confirm signer identity with Android SDK tools as well
as the manifest comparison. On a **disposable Android test user/profile**
with synthetic task records, verify an actual in-place same-package upgrade
without uninstalling, then check that the legacy WebView record set, selected
native SQLite source, protected rollback vault, saved views, tags and task
edits survive restart. Test Cancel/Back and system document picker failures.
Do not apply storage fault injection to a primary daily-use handset.

Log the device model, OS, IME, app versionCodes, **public certificate digest**,
the pass/fail steps and sanitized observations. Never attach real task text,
private SQLite backups, APK signing keys or account tokens.

M2.5's release hold remains active until this rehearsal, document-provider
interruption tests, genuine handset interaction checks, and the explicit
security/release review have been signed off.
